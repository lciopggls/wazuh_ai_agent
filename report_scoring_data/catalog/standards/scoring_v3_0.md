## 一、评分目的

本评分框架用于评价攻击溯源智能体和基线智能体生成的最终调查报告质量。

评分重点不是报告篇幅、排版或措辞是否华丽，而是报告是否：

1. 正确理解用户提供的初始日志；
2. 找到调查范围内可访问、可检索的关键证据；
3. 正确重建进程链和行为之间的因果关系；
4. 按正确的相对顺序组织攻击时间线；
5. 明确表达并合理映射 MITRE ATT&CK 技术；
6. 与 Ground Truth 保持一致，并正确描述未发生的行为；
7. 避免同一错误在多个指标中被重复重罚。

每份报告满分为 100 分，共包含六个评分维度。任意单个指标的最低得分均为 0 分，不得出现负分。

本评分标准只规定报告质量如何评分，不规定两个智能体之间的提升比例及其计算方式。

### 1.1 v3.0 版本变更说明

v3.0 完整继承 v2.0 的六个评分维度、权重和其他计分规则，仅修改第 7.2 节“MITRE ATT&CK 基础表达”的判定方式，并同步调整相关引用文字。

基础表达采用 `0/5/15` 三级评分：没有合格表达得 0 分，至少一个但未覆盖全部攻击时间线项目得 5 分，全部攻击时间线项目均完整表达得 15 分。其他评分维度及 MITRE ATT&CK 映射质量的计分方式保持不变。

### 1.2 六维度名称同步说明

2026-08-25 对六个评分维度的正式中文名称进行全链路统一。本次只调整维度名称及对应语义表述；结构化字段、`10/20/5/20/30/15` 权重、总分 100 分和全部计分规则保持不变。历史评分记录继续按其生成时的名称和版本保留，不回写、不覆盖。

## 二、评分维度与权重

| 评分维度 | 权重 | 核心问题 |
|---|---:|---|
| 初始事件识别准确性 | 10 | 是否正确理解初始日志中的核心主体、对象和行为 |
| 关键证据检索与覆盖度 | 20 | 可访问、可检索的关键证据是否被找到并写入报告 |
| 事件时间线准确性 | 5 | 核心行为顺序是否正确，时间表达是否自洽 |
| 攻击链重建与因果分析 | 20 | 执行链、行为状态和因果边界是否解释正确 |
| MITRE ATT&CK 映射质量 | 30 | 是否明确表达 ATT&CK 技术，且映射合理 |
| 未发生行为核验 | 15 | 对未发生行为的结论是否正确、是否有依据 |
| **总分** | **100** | |

## 三、初始事件识别准确性：10 分

### 3.1 评分目标

检查报告是否准确理解并复述用户提供的初始日志。初始事件识别准确性评价的是调查起点，不代表完整溯源是否完成。

### 3.2 子项与分值

| 子项 | 分值 | 主要检查内容 |
|---|---:|---|
| Agent、主机和用户身份 | 2 | Agent ID、主机名、IP、用户名和登录上下文 |
| 锚点进程关系 | 3 | 锚点进程、父进程、PID、父 PID、ProcessGuid、ParentProcessGuid |
| 关键命令与对象 | 3 | 命令行、进程路径、文件路径、注册表路径、任务名称等 |
| 事件类型与实际动作 | 2 | 进程创建、查询、写入、文件创建、任务创建等动作是否识别正确 |

### 3.3 不作强制要求的字段

报告不需要为了获得初始事件识别准确性分数而强制展示：

- 原始 Sysmon 时间；
- Wazuh 规则 ID；
- Wazuh 规则等级；
- Wazuh 规则描述。

处理原则：

```text
未展示上述字段
→ 不扣分

主动展示且内容正确
→ 不额外加分

主动展示但内容错误或属于虚构
→ 在相关锚点子项内扣分
```

例如，Archives 锚点本身没有 `rule.id` 时，报告不写规则 ID 不扣分；如果主动编造规则 ID，则仍属于事实错误。

### 3.4 高分表现

- 正确识别 Agent、主机、用户和告警进程；
- 正确区分锚点进程与父进程；
- 保留关键 PID、ProcessGuid、命令行、路径和对象名称；
- 正确识别初始日志记录的实际动作；
- 不把查询写成修改，不把定义中的动作写成已经执行。

### 3.5 典型扣分情况

- 写错 Agent、主机、用户或核心 PID；
- 颠倒父进程与子进程；
- 改写或截断导致关键命令含义发生变化；
- 写错文件、注册表或任务路径；
- 把 `reg query` 写成注册表写入；
- 把任务定义中的命令写成已经创建的进程；
- 主动展示错误或虚构的规则、等级、时间等字段。

## 四、关键证据检索与覆盖度：20 分

### 4.1 评分目标

检查智能体是否找到并在最终报告中呈现当前场景、调查范围和现有工具条件下能够访问或检索的关键证据。

本维度继续采用整体评分，不要求为每个场景额外维护逐项证据清单。

### 4.2 主要检查内容

- 父进程、祖先进程、子进程和适用的同级进程；
- PID、父 PID、ProcessGuid 和 ParentProcessGuid 关系；
- 文件创建、删除和修改；
- DLL 或模块加载；
- 注册表创建、写入、查询和删除；
- 计划任务创建、查询和适用的任务证据；
- 网络连接和 DNS 查询；
- 服务、账户、登录和权限事件；
- 运行结果文件和验证命令；
- 攻击行为产生且可通过当前工具检索的副作用。

### 4.3 高分表现

- 从锚点向上恢复适用的父进程和祖先进程；
- 从锚点向下恢复适用的子进程；
- 找到核心行为及其验证动作；
- 找到可检索的注册表、文件、计划任务和网络等证据；
- 使用 PID、ProcessGuid、路径、任务名、RUN ID 等线索关联事件；
- 将查到的关键证据写入最终报告；
- 对确实存在的遥测缺口进行说明。

### 4.4 典型扣分情况

- 只复述初始告警，没有继续调查；
- 遗漏可检索的关键父进程或子进程；
- 遗漏同一脚本创建的其他核心进程；
- 遗漏可检索的查询、验证或副作用证据；
- 执行了查询，但最终报告没有呈现查到的关键证据；
- 大量查询无关噪声，却遗漏核心行为；
- 将查询次数多或报告篇幅长当成关键证据检索与覆盖充分。

### 4.5 可见性与遥测边界

关键证据检索与覆盖度只评价以下内容：

1. 用户初始输入中直接可见的证据；
2. 智能体通过当前可用工具能够访问或检索的证据。

以下内容不得仅因为报告没有提及而扣召回分：

- 脚本中的说明性 `NOTE`；
- 只有测试人员或评分 AI 知道的场景设计事实；
- 智能体无法读取的 manifest 文件内容；
- Archives 中不存在的日志；
- 当前工具无法验证的文件不存在、行为未发生等结论。

如果智能体只能看到 manifest 文件路径，而不能读取文件内容，则只评价其是否识别文件路径，不要求复述 manifest 内部字段。

## 五、事件时间线准确性：5 分

### 5.1 评分目标

检查报告是否按照正确的相对顺序组织核心攻击行为，并保持时间表达内部一致。

本版本不规定必须优先使用 Sysmon 原始时间。Wazuh 接收时间或 Sysmon 事件时间均可用于报告。

### 5.2 子项与分值

| 子项 | 分值 | 评分要求 |
|---|---:|---|
| 核心事件相对顺序正确 | 3 | 创建、查询、验证、触发、执行等行为的先后顺序正确 |
| 报告内部时间一致 | 1 | 同一事件在报告不同位置的时间不互相矛盾 |
| 无虚构年份、日期或时间 | 1 | 不编造不存在的年份、日期或时间 |

### 5.3 评分原则

- 不因 Wazuh 时间和 Sysmon 时间相差数秒而扣分；
- 不强制保留毫秒精度；
- 不强制解释时间字段来源；
- 只要核心行为相对顺序正确，即可获得本维度主要分数；
- 把 2026 年写成 2016 年，扣除“无虚构时间”子项；
- 如果时间错误造成核心因果顺序颠倒，则影响“核心事件相对顺序”子项；
- 本维度最低为 0 分。

## 六、攻击链重建与因果分析：20 分

### 6.1 评分目标

检查报告是否正确重建谁启动了谁、谁修改了什么、什么行为真正执行，以及不同事件之间是否存在证据支持的因果联系。

### 6.2 子项与分值

| 子项 | 分值 | 主要检查内容 |
|---|---:|---|
| 核心进程链重建 | 12 | 父子进程、PID、ProcessGuid 和核心执行路径 |
| 行为状态区分 | 5 | 创建、写入、查询、验证、触发和执行的区别 |
| 因果边界控制 | 3 | 是否错误纳入时间重叠噪声、无关进程或无证据机制 |

### 6.3 核心链优先原则

如果报告已经正确重建核心父子进程和主要行为链，应优先保留“核心进程链重建”的得分。

附加的无证据结论不应自动推翻已经正确的核心链。例如：

```text
报告正确还原 powershell.exe → reg.exe
但错误附加“可能存在进程注入”
```

这种情况下：

- 正确的核心进程链得分继续保留；
- 注入误判主要影响行为状态区分和因果边界控制；
- 只有错误结论反过来扭曲攻击入口、父子关系或主要执行机制时，才进一步影响核心链得分。

### 6.4 无证据注入的分级处理

对于 Event ID 10、高 `GrantedAccess`、`UNKNOWN` 栈帧等进程访问证据，应根据报告措辞和实际影响分级处理：

- “需要进一步验证是否存在注入”：不扣分或轻微扣分；
- “疑似注入”，但不是核心结论：有限扣分；
- “确认注入”或“确认 Shellcode 执行”：较多扣分；
- 将注入作为核心攻击机制并据此改写整条攻击链：可以影响更多子项。

不得仅因一次附加注入误判直接将本维度清零。

### 6.5 未发生行为的遗漏规则

如果攻击脚本实际未执行某种行为，但最终报告没有说明该行为未发生：

```text
不加分，也不扣分
```

如果报告主动调查并正确说明未发生，可以在“未发生行为核验”维度获得分数。

如果报告错误声称该行为已经发生，则根据错误措辞、证据和对核心攻击结论的影响程度扣分。

### 6.6 必须正确区分的典型状态

#### SIM-101

```text
Base64 被写入注册表
≠
Base64 被解码或执行
```

#### SIM-102

```text
ONLOGON 计划任务已创建
≠
ONLOGON 触发器已触发
≠
任务动作 cmd.exe 已执行
```

#### SIM-103

```text
PowerShell 收到 EncodedCommand
+
解码后的命令实际执行
```

### 6.7 典型扣分情况

- 把查询操作写成修改或创建；
- 把 Base64 存储写成 Base64 执行；
- 把计划任务创建写成任务已经触发；
- 把任务查询写成新的持久化创建；
- 把命令行中的文件路径写成文件已经创建；
- 把 Event ID 10 进程访问直接写成进程注入；
- 把正常 PowerShell 初始化文件写成攻击载荷；
- 把仅有时间重叠的 VMware、OneDrive、preflight、cleanup 或其他场景事件强行并入核心链。

## 七、MITRE ATT&CK 映射质量：30 分

### 7.1 评分目标

检查报告是否在攻击时间线中明确表达 MITRE ATT&CK 技术，以及行为、技术名称和技术编号之间的对应关系是否合理。

本维度由“基础表达”和“映射质量”两部分组成。

### 7.2 基础表达：15 分

基础表达只能取以下三个分值：

```text
0 分
5 分
15 分
```

#### 7.2.1 获得基础表达分的共同条件

获得 5 分或 15 分，必须同时满足：

1. 报告中至少有一个攻击时间线项目，在同一项目内明确包含时间、至少一个具体 T 编号和对应行为；
2. 该项目中至少有一个 T 编号采用有效格式 `Txxxx` 或 `Txxxx.xxx`；
3. 全部攻击时间线项目中，至少存在一个基本合理的“行为—T 编号”对应。

如果报告中不存在任何可识别的攻击时间线项目，基础表达为 0 分。

#### 7.2.2 三级分档规则

##### 0 分：没有形成有效基础表达

符合以下任一情况，基础表达为 0 分：

- 报告不存在任何可识别的攻击时间线项目；
- 没有任何攻击时间线项目在同一项目内同时包含时间、有效格式的具体 T 编号和对应行为；
- 时间、T 编号和行为需要跨不同项目或章节拼接才能形成对应；
- 所有“行为—T 编号”对应均明显不合理。

##### 5 分：形成部分基础表达

获得 5 分必须同时满足：

- 至少一个攻击时间线项目在同一项目内完整包含时间、有效格式的具体 T 编号和对应行为；
- 至少存在一个基本合理的“行为—T 编号”对应；
- 仍有至少一个其他攻击时间线项目没有完整包含时间、有效格式的具体 T 编号和对应行为。

##### 15 分：形成完整基础表达

获得 15 分必须同时满足：

- 报告中的每一个攻击时间线项目，均在同一项目内明确包含时间、至少一个有效格式的具体 T 编号和对应行为；
- 全部攻击时间线项目中，至少存在一个基本合理的“行为—T 编号”对应。

如果报告只有一个攻击时间线项目，该项目完整且映射基本合理，则获得 15 分；该项目不完整或映射明显不合理，则获得 0 分，不能获得 5 分。

#### 7.2.3 攻击时间线项目的判定

攻击时间线项目根据条目实际表达的行为性质判定，而不是简单按照所在章节或排版形式判定。

以下内容视为攻击时间线项目：

- 报告以时间节点形式陈述已经发生的攻击行为、可疑行为或攻击链行为；
- 一个时间节点同时包含攻击行为和调查说明时，该节点仍视为攻击时间线项目。

以下内容不视为攻击时间线项目：

- 调查人员或报告生成过程中的证据查询、验证和分析操作；
- 单纯的告警接收说明；
- 正常系统活动；
- 否定性结论，例如“未发现外联行为”；
- 不包含具体攻击行为的总结性文字。

攻击者实施的查询、验证或侦察行为仍属于攻击时间线项目，不得与调查人员的调查操作混淆。

#### 7.2.4 项目划分规则

攻击时间线项目按报告中的时间表达划分：

- 每出现一个独立的时间点或时间范围，对应一个攻击时间线项目；
- 相同时间值在不同叙述单元中重复出现时，分别计算为不同项目。例如两条内容均写为 `15:01`，仍按两个项目检查；
- 连续段落中出现多个时间点，并分别描述不同攻击行为时，按多个项目检查；
- 一个时间点下描述多个攻击行为时，仍视为一个项目。

#### 7.2.5 同一项目内的完整表达

时间、具体 T 编号和对应行为必须在同一个独立时间节点、列表项目或表格行中形成直接、无歧义的对应。

允许：

- 同一项目通过换行、缩进或同一表格行的不同单元格表达三项信息；
- 使用完整日期时间、仅时分秒、带毫秒的时间、明确时间范围或带有明确时间值的近似表达，例如“约 15:45”。

不允许：

- 跨不同时间节点、不同列表项目、不同表格行或不同章节拼接三项信息；
- 从前一个项目继承时间或 T 编号；
- 只使用“随后”“之后”“接着”“早期阶段”等不含明确时间值的相对顺序描述；
- 在时间线中只写行为，再通过报告其他位置集中列出的 T 编号补足基础表达。

#### 7.2.6 多行为项目与基本合理映射

一个攻击时间线项目包含多个攻击行为时，只要求该项目至少出现一个具体 T 编号，并能与项目中的至少一个行为形成对应；不要求项目中的每个独立行为都分别标注 T 编号。未标注行为对核心技术覆盖程度的影响由“映射质量”评分。

“基本合理”是最低语义门槛：只要 T 编号所代表的技术与同一项目中的至少一个行为在基本语义上相符，即可认定为基本合理。基础表达不要求必须使用最精确的子技术；主技术与子技术的粒度、技术名称精度以及其他错误映射由“映射质量”评分。

只要至少存在一个基本合理的“行为—T 编号”对应，基础表达档位就由合格攻击时间线项目的覆盖情况决定。其他项目的映射即使存在错误，也不降低已经满足的基础表达档位，只影响映射质量。

15 分示例：

```text
15:01 / T1059.001：PowerShell 执行编码命令
15:02 / T1053.005：创建计划任务
```

两个攻击时间线项目都完整包含时间、具体 T 编号和行为，并且至少一个映射基本合理，因此基础表达为 15 分。

5 分示例：

```text
15:01 / T1059.001：PowerShell 执行编码命令
15:02：创建计划任务
```

第一项完整且映射基本合理，但第二项缺少具体 T 编号，因此基础表达为 5 分。

0 分示例：

```text
15:01：PowerShell 执行编码命令
15:02：创建计划任务
```

没有任何攻击时间线项目形成“时间＋具体 T 编号＋行为”的完整表达，因此基础表达为 0 分。

基础表达只评价时间线中的表达覆盖情况和最低语义合理性。其他映射问题只影响映射质量。

### 7.3 映射质量：15 分

| 子项 | 分值 | 主要检查内容 |
|---|---:|---|
| 核心技术覆盖程度 | 6 | 是否覆盖场景实际发生的主要攻击技术 |
| 行为与技术对应准确性 | 6 | 技术是否绑定到正确行为和正确发生点 |
| 技术名称及子技术精度 | 3 | 中文技术名称、主技术和子技术粒度是否准确 |

评分原则：

- 没有 T 编号，但技术中文名称和行为对应正确，仍可获得映射质量分；
- 有部分正确、部分错误时，保留正确映射获得的分数；
- 错误加入 `T1055`、`T1105` 等技术，只在映射质量 15 分范围内按严重程度影响得分；
- 错误映射不影响已经获得的基础表达 5 分或 15 分；
- 映射质量最低为 0 分，不得倒扣基础表达或其他指标。

### 7.4 合理映射示例

- 注册表修改：`T1112 / Modify Registry`；
- 创建计划任务：`T1053.005 / Scheduled Task/Job: Scheduled Task`；
- PowerShell 执行：`T1059.001 / Command and Scripting Interpreter: PowerShell`；
- Windows 命令行执行：`T1059.003 / Windows Command Shell`；
- 有证据支持的 Base64 混淆：`T1027 / Obfuscated Files or Information`。

### 7.5 典型映射问题

- 将 `reg query` 映射为注册表修改或持久化；
- 把自定义非自启动注册表键认定为持久化位置；
- 将 VMware 拖放自动认定为 `T1105`；
- 仅凭 Event ID 10、高 `GrantedAccess` 或 `UNKNOWN` 栈帧映射 `T1055`；
- 把 PowerShell 策略测试文件映射为隐藏文件技术；
- 对没有发生的凭据访问、横向移动或外传进行映射；
- 为了让报告看起来全面而堆砌技术编号。

## 八、未发生行为核验：15 分

### 8.1 评分目标

检查报告对 Ground Truth 明确未发生行为的判断是否正确。报告主动给出正确的肯定式负面结论时应获得分数；没有提及则不加分也不扣分。

本维度按行为逐项累计，不因一个错误行为直接清空整个指标。

### 8.2 正确结论加分

对于 Ground Truth 明确未发生的每一种行为：

```text
报告明确、肯定地说明该行为未发生
→ 加 2 分

报告同时提供查询范围、日志结果或其他证据依据
→ 再加 1 分

报告没有提及
→ 0 分，不加分也不扣分
```

例如：

```text
“没有发生网络通信”
→ 与 Ground Truth 一致，加 2 分

“针对 PID 6392 和 PID 7580 查询 Event ID 3、22，
在指定时间范围内未返回网络或 DNS 日志”
→ 再加 1 分，该行为共获得 3 分
```

### 8.3 错误结论分级扣分

如果报告声称 Ground Truth 明确不存在的行为已经发生，根据措辞和影响程度扣分：

| 错误程度 | 建议扣分 |
|---|---:|
| 仅表示需要进一步调查，未声称已经发生 | 0～1 |
| 使用“疑似、可能”等措辞声称发生 | 0.5～1.5 |
| 明确声称行为已经发生 | 1～2 |
| 将不存在的行为作为核心攻击结论反复确认 | 2～3 |

错误只影响对应行为及其严重程度。其他行为判断正确获得的分数继续保留。

### 8.4 计算方式

```text
本维度得分
= min(15, max(0, 正确结论加分 - 错误结论扣分))
```

例如，报告正确说明没有网络、没有外传和没有凭据访问，同时错误声称存在横向移动，应保留前三项已经获得的分数，只对横向移动错误进行有限扣分。

### 8.5 可见性边界

- Ground Truth 可用于判断报告结论是否与事实矛盾；
- 不得因为报告没有复述脚本 `NOTE` 或其他不可见事实而扣分；
- 没有提及某项未发生行为时，不加分也不扣分；
- 报告主动给出与 Ground Truth 一致的肯定式负面结论，即使没有展示日志依据，也可以获得每项 2 分；
- 展示调查依据后，才能获得该行为额外的 1 分。

## 九、攻击场景定性原则

本版本删除“授权实验定性”评分维度。评分时统一按照攻击脚本和攻击行为本身进行分析，不因报告使用以下措辞而扣分：

- 攻击者；
- 失陷主机；
- 恶意脚本；
- 恶意载荷；
- 攻击行为；
- 建议隔离或处置。

删除的是授权实验语境和措辞处罚，不豁免具体事实错误。

例如：

```text
把脚本称为“恶意脚本”
→ 不因该措辞扣分

Ground Truth 没有网络下载，
报告却明确声称下载并执行了外部载荷
→ 属于具体行为误判，仍需在相关指标中扣分
```

## 十、统一评分原则

### 10.1 每份报告独立评分

每个智能体、每个场景、每次独立运行都必须单独评分。

不得：

- 用 R2 的证据补充 R1；
- 用另一个智能体的结论补充当前智能体；
- 因为三次运行中有一次正确，就给另外两次增加分数；
- 用 State 或查询记录替最终报告补充得分。

State 和查询记录可以用于审计，但最终报告没有使用的关键证据，不视为报告已经正确呈现。

### 10.2 单项最低分和评分粒度

- 任意单个评分指标最低为 0 分，不得出现负分；
- MITRE 基础表达只能取 0 分、5 分或 15 分；
- 其他指标和子项以 0.5 分为最小评分单位；
- 每项得分不得超过其权重；
- 总分为六个指标之和，保留 1 位小数；
- 不允许使用缺乏明确依据的过度精细小数。

### 10.3 同一根因错误的重复扣分限制

同一个根因错误最多影响两个直接相关指标，不得在三个及以上指标中重复扣分。

例如：

```text
Event ID 10 / UNKNOWN
→ 错误认定进程注入
→ 错误映射 T1055
```

该错误可以影响：

1. 攻击链重建与因果分析中的行为状态或因果边界；
2. MITRE ATT&CK 映射质量中的映射质量。

不得再以相同理由在初始事件识别准确性、关键证据检索与覆盖度、未发生行为核验等指标中重复扣分。

其他示例：

- 写错年份主要计入事件时间线准确性；
- 遗漏关键子进程主要计入关键证据检索与覆盖度；
- 找到子进程但解释错父子关系主要计入攻击链重建与因果分析；
- 一个或多个攻击时间线项目未按第 7.2 节完整输出时间、具体 T 编号和对应行为，只影响 MITRE 基础表达。

### 10.4 Ground Truth 的两种用途

Ground Truth 和 manifest 的使用必须区分“矛盾判断”和“遗漏判断”。

#### 判断报告是否与事实矛盾

可以参考：

```text
Ground Truth / manifest
→ 原始 Wazuh 日志
→ 智能体实际执行的查询和调查状态
→ 最终报告
```

Ground Truth 可以用于判断报告是否错误声称发生了实际不存在的行为。

#### 判断报告是否遗漏证据

只能考虑：

1. 用户初始输入直接包含的证据；
2. 智能体通过当前工具实际能够访问或检索的证据。

不得因为 Ground Truth、脚本或评分人员知道某项事实，就默认智能体也必须知道并写入报告。

### 10.5 有效报告与基础设施失败

- API 连接失败、Indexer 不可用、线程异常等属于基础设施失败；
- 基础设施失败应保留错误记录，但不计入有效报告平均分；
- 需要补跑，直到取得规定数量的有效报告；
- 线程正常完成但报告质量差、遗漏证据或出现事实错误，仍属于有效测试结果；
- 不能因为报告得分低而重跑替换。

### 10.6 查询次数不直接计分

- 查询次数多不代表报告质量高；
- 查询必须与调查目标相关；
- 查询结果必须被正确解释并进入最终报告；
- 无关查询、重复查询和错误解释不会获得额外分数。

### 10.7 报告形式不直接计分

以下内容本身不增加质量分：

- 报告篇幅；
- 表格数量；
- 排版美观；
- 攻击图复杂度；
- 专业词汇数量；
- 建议数量。

MITRE 时间线基础表达按照本标准第 7.2 节单独评分，不属于单纯的排版加分。

### 10.8 调查耗时不参与质量评分

- 智能体运行耗时只作为参考；
- 不因查询时间短直接加分；
- 不因调查时间长直接扣分；
- 如果需要比较速度，应单独建立边界一致的性能指标。

### 10.9 暂不采用身份盲评

本版本暂不要求隐藏智能体名称或随机打乱报告顺序。评分 AI 可以按照现有文件组织方式读取报告，但必须对两个智能体应用相同的评分标准和权重。

## 十一、评分时的核心判断顺序

对每份报告建议按照以下顺序评分：

1. 读取 Ground Truth、预期行为和已知遥测边界；
2. 核对原始锚点日志；
3. 阅读最终报告，不先使用其他运行补充当前报告；
4. 评分锚点身份、进程、命令、对象和事件动作；
5. 评价可访问证据的召回情况；
6. 检查核心事件相对顺序、内部时间一致性和虚构时间；
7. 分别评分核心进程链、行为状态和因果边界；
8. 检查 MITRE 基础表达是否满足 0/5/15 分条件；
9. 评分 MITRE 核心覆盖、行为对应和名称精度；
10. 按行为累计正确负面结论和证据支撑分；
11. 对错误声称发生的行为按严重程度有限扣分；
12. 检查同一根因是否在三个及以上指标中重复扣分；
13. 检查每项得分是否在 0 到对应权重之间；
14. 以 0.5 分为最小单位记录各项得分并计算总分；
15. 最后查看 State 和查询记录进行审计，不得用其替最终报告补分。

## 十二、评分结果应保存的内容

每次评分文件至少应记录：

- 场景编号；
- 智能体名称；
- 运行编号；
- 线程 ID；
- 输入 SHA256；
- 锚点 `_index` 和 `_id`；
- State、报告和查询记录文件名；
- 运行统计；
- Ground Truth 和遥测边界说明；
- 六个维度的权重；
- 六个维度的实际得分；
- 各内部子项得分；
- MITRE 基础表达得分和映射质量得分；
- 负面结论的加分项和错误结论扣分项；
- 每个维度的评分理由；
- 同一根因错误涉及的指标；
- 做得好的地方；
- 主要问题；
- 总分；
- 是否属于有效报告。

## 十三、评分框架总结

本评分框架最看重以下四点：

### 1. 起点正确

准确理解 Agent、主机、用户、进程、命令、对象和事件动作，不强制展示非核心规则与原始时间字段。

### 2. 查得充分

找到并呈现智能体实际可访问、可检索的核心证据，不要求复述脚本或评分侧独有信息。

### 3. 链路和映射清晰

正确重建核心进程链，区分创建、查询、验证、触发和执行，并在每一个攻击时间线项目中完整表达时间、具体 T 编号和对应行为。

### 4. 结论与事实一致

对 Ground Truth 明确未发生的行为，报告主动给出正确结论应获得分数；一个错误行为不能清空其他正确结论，也不能在多个指标中被无限重复处罚。

一份高质量攻击溯源报告应当做到：

> 锚点核心事实正确、可见证据充分、时间顺序清晰、核心链路准确、MITRE 表达明确、结论与 Ground Truth 一致。
