# 报告评分智能体：最终目标与固定约束

> 更新日期：2026-08-28
> 文档性质：长期产品目标和验收边界

## 1. 最终目标

建设一个可独立运行、也可由项目完整前后端调用的报告评分智能体，对不同攻击溯源智能体生成的
报告进行统一、可追溯、可比较的质量评估。

评分只消费测试前已经保存在本机的完整案例答案。系统不负责在普通测试过程中创建案例或生成
标准答案。

## 2. 两个正式报告入口

### AI 对话报告

测试员将本地既有案例对应的完整 JSON 日志交给攻击溯源智能体。智能体生成最终报告后，测试员
选择对应案例和被测智能体，可以直接保存并登记评分，也可以只保存到本机。

### 本机报告

测试员上传智能体已经生成的 Markdown 或文本报告，并选择对应的本地案例和被测智能体。系统
直接使用该案例预置的评分材料。本入口不要求上传锚点、运行包或答案包。

两个入口在登记后共用同一套报告持久化、评分、详情、历史和对比链路。

## 3. 已有固定案例与新攻击案例

SIM-204～SIM-206 是仓库当前预置的固定基准。重测这些案例时直接使用其既有
`input_message.txt` 和正式答案目录，不重新生成答案。

新攻击案例不要求恢复页面内的动态案例准备功能。案例设计人员在执行攻击前保存计划答案，执行
后使用真实运行记录和 Wazuh 证据修订为正式答案，再安装到本机案例目录。案例启用并通过完整性
校验后，使用与固定基准完全相同的两个报告入口。完整文件清单和角色隔离要求见
`12_NEW_HOST_NEW_ATTACK_TEST_FLOW.md`。

## 4. 固定约束

- 案例答案必须在测试前由具备相应知识的人员准备、审核并保存在评分主机。
- Ground Truth、telemetry boundary、expected report 和评分标准不得提供给被测智能体。
- 普通测试员不能通过页面创建、编辑、确认或发布案例。
- 未评分、评分失败和模型不可用必须显示明确状态，不能伪装为 0 分。
- 总分由服务端根据六个维度和扣分规则重算，前端只消费验证后的结构化结果。
- 同一报告登记和评分请求必须具备幂等边界；重评分必须显式发起。
- Thread ID、Run ID 和备注是可选审计字段，不是评分门槛。
- 功能开关关闭时不得影响正式 AI 助手等主流程。
- 系统信任测试员选择的报告与本地案例对应关系；当前不额外要求锚点文件来证明报告来源。

## 5. 不属于当前目标

- 测试时动态创建新案例；
- 上传或生成 `anchor.json`、`run-package.zip` 或 `scoring-package.zip`；
- 在线查询并冻结 Archives；
- 由测试员填写 Ground Truth、遥测边界或预期报告；
- 自动生成标准答案或从待评分报告反推答案；
- 把同一攻击脚本的新一次运行自动变成新案例；
- 自动执行攻击、修改 Wazuh/Sysmon 配置或清理测试机；
- 本阶段完成模型分数与人工分数的精确校准。

## 6. 文档优先级

- `11_FIXED_BENCHMARK_SCORING_REQUIREMENTS.md`：当前产品需求和验收事实源；
- `12_NEW_HOST_NEW_ATTACK_TEST_FLOW.md`：新主机新案例的文件准备与测试操作流程；
- `00_CURRENT_PROJECT_STATE.md`：当前工作树、实现和验证状态；
- 本文：长期目标和不可突破的产品边界。
